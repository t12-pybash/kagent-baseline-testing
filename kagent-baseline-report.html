kagent Baseline Test

2026-11-10 Author: Ciaran Donegan kagent v0.10.6 Status: Continuous

Fleet footprint baseline for the kagent agent framework on a 5-node bare-metal cluster. 102 pods deployed concurrently across 6 agent types, all running simultaneously. Idle memory and CPU measured from Prometheus. Establishes the per-pod resource floor for capacity planning a 100-agent fleet on EKS.

All Go agent types converge at 6.6-7.7 MB idle RSS regardless of system prompt size, tools, or conversation state. Python ADK pods idle at 219 MB -- 33x more. All 6 types reached full concurrent deployment; linear scaling confirmed across the board.

Test Environment

Local 5-node bare-metal Kubernetes cluster: 2 schedulable worker nodes (wk1: 4 CPU, 10.5 GB; wk4: 12 CPU, 38.8 GB) and 3 control plane nodes with untolerated taints. kagent installed via Helm from the upstream OCI chart. Model gateway: LiteLLM (proxying Claude Sonnet 5.5 via the Anthropic API).

All 6 agent deployments scaled to 17 replicas simultaneously (102 target pods total) in namespace kagent. All 102 pods reached Ready. Prometheus memory and CPU scraped after a 13-minute settle window with all pods running concurrently at idle.

Idle footprint test: pods running but not serving requests. The question is what 100 agents cost the cluster before anyone calls them.

Findings

1. Go vs Python runtime memory

All 5 Go-runtime agent types idle at 6.6-7.7 MB RSS regardless of system prompt size, tool definitions, or conversation state. Python-runtime pods idle at 219 MB -- 33x more than go-minimal. The difference is the Python interpreter and google-adk package overhead, present in every pod regardless of what the agent does. At 100 pods, Go costs 659-766 MB; Python costs 21.4 GB. The kagent controller itself is always Go; the runtime choice only affects each agent pod.

2. Tool schema cost is in tokens, not footprint

go-k8s-tools carries full Kubernetes tool schemas in its system prompt yet idles at 7.7 MB -- near-identical to go-minimal at 6.6 MB. Tool definitions, system prompt size, and conversation state have no effect on idle pod footprint. For capacity planning, all Go types can be treated as equivalent at idle regardless of tool configuration.

3. Fleet is memory-bound at idle

CPU usage across all 6 types is negligible at idle -- 0.70-1.59 m per pod. The fleet sizing constraint is entirely memory. A mixed 100-agent fleet (all 6 types) requires approximately 25 GB RAM. A Go-only fleet of 100 agents requires under 800 MB. Runtime choice is the dominant capacity planning variable.

Gaps vs Production Stack

  • Inference stack not installed (llm-d, Envoy Gateway, OPA, Valkey) -- none of these affect idle pod footprint. They sit outside the agent pods and only matter at request time.
  • llmops-agents chart not used -- the production chart adds an external Postgres sidecar for agent state persistence. That sidecar is not in these numbers and would add per-pod memory on EKS; worth a follow-up measurement.
  • Model and vCluster bridged -- claude-sonnet-5-5 via Anthropic API rather than Bedrock; behaviour and cost profile are equivalent. vCluster cappuccino installed and confirmed: agent call completed, namespace isolation verified.
Footprint figures should hold on EKS. kagent is model-agnostic and the Go runtime overhead is independent of the inference layer.
