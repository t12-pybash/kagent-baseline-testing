kagent Baseline Test

2026-11-10 Author: Ciaran Donegan kagent v0.10.6 Status: Continuous

Fleet footprint baseline for the kagent agent framework on a 5-node bare-metal cluster. 102 pods deployed concurrently across 6 agent types (17 per type). Idle memory and CPU measured from Prometheus with all pods running simultaneously. Establishes the per-pod resource floor for capacity planning a 100-agent fleet on EKS.

All Go agent types converge at approximately 7 MB idle RSS regardless of system prompt size, tools, or conversation state. Python ADK pods idle at 219 MB -- 32x more. Linear scaling confirmed for 3 of 6 types with full 17-pod concurrent data. Worker node scheduling limits (CPU request ceiling, 110 pods per node) prevented full deployment for the remaining 3 types; per-pod figures are consistent with the Go runtime baseline.

Test Environment

Local 5-node bare-metal Kubernetes cluster: 2 schedulable worker nodes (wk1: 4 CPU, 10.5 GB; wk4: 12 CPU, 38.8 GB) and 3 control plane nodes with untolerated taints. kagent installed via Helm from the upstream OCI chart. Model gateway: LiteLLM (proxying Claude Sonnet 5.5 via the Anthropic API).

All 6 agent deployments scaled to 17 replicas simultaneously (102 target pods total) in namespace kagent. Prometheus memory and CPU scraped after a 13-minute settle window once pods reached Ready. Worker node scheduling limits (CPU request exhaustion and 110-pod-per-node ceiling) prevented full deployment: 77 of 102 pods reached Ready. go-long-context (8 pods) and go-multiturn (2 pods) are partial samples; per-pod figures are consistent with the Go runtime baseline from the other 4 types.

Findings

1. Go vs Python runtime memory

All 5 Go-runtime agent types idle at 6.8-7.2 MB RSS regardless of system prompt size, tool definitions, or conversation state. Python-runtime pods idle at 219 MB -- 32x more than go-minimal. The difference is the Python interpreter and google-adk package overhead, present in every pod regardless of what the agent does. At 100 pods, Go costs 680-720 MB; Python costs 21.9 GB. The kagent controller itself is always Go; the runtime choice only affects each agent pod.

2. Tool-use cost and latency

The k8s-tools agent uses 3,263 prompt tokens vs 642 for a minimal agent -- 5x more prompt tokens, 5.8x more total cost per call. The difference comes from Kubernetes tool schemas injected into the system prompt. Latency averaged 6.3s -- Claude resolves k8s-tools tasks in a single tool-use round trip rather than multiple loops. All 17 runs completed successfully. At idle, go-k8s-tools memory (7.2 MB) is indistinguishable from go-minimal (6.8 MB) -- the tool schema cost is in tokens, not pod footprint.

3. Tool-call compliance: Claude vs Ollama

All Go agents completed with zero tool-call errors against Claude Sonnet 5.5. The go-multiturn agent returned input-required on 5 of 17 runs. This is correct behaviour for an intentionally ambiguous prompt. Against Ollama, 95 of 102 runs returned input-required regardless of agent type. This is a model compliance issue, not a framework issue. Ollama could not follow the system prompt instructions. See the Model Compliance section above.

These results establish a kagent agent framework overhead baseline - pod footprint, token throughput, and latency per agent type. The inference layer (llm-d vs LiteLLM) and model (Sonnet 5 vs Ollama) are the two biggest gaps for cost and latency accuracy. Memory and CPU footprint for agent pods should hold on EKS since kagent itself is model-agnostic.

Production Gateway Architecture

The Envoy Gateway enforces three things in sequence for every request:

1. Identity

The caller presents a Kubernetes ServiceAccount token. The gateway verifies it and strips any identity headers the client tries to inject. Tenants in vClusters get the token automatically.

2. Authorisation

OPA checks whether this tenant is allowed to call this agent or model. Tenant permissions are managed in a config file and update live without restarting the gateway.

3. Quota

Token usage is counted per response and charged against the tenant's quota in a shared counter store. Requests from tenants over their limit are blocked before reaching the model.
